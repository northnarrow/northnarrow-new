# Stage S1: the round on six kernels and the kernel census (lot 1.5)

Stage S1 (verifier margin, the aya-ebpf 0.3 compiler, the 7.0 fallbacks
that see every CPU, the `.rpm`) ends with one lab round on `main` as it is,
on six kernels: every program of the eBPF object through each verifier,
the privileged suites on 5.15 and 7.0, the per-call cost of the sensors on
5.15 and 6.8, the `.rpm` lifecycle on AlmaLinux 9, and a census of the
kernel facts the agent relies on. This file is the evidence for the stage's
exit criteria
([`KERNEL_COMPATIBILITY.md`](../../operator/KERNEL_COMPATIBILITY.md),
"Older verifiers" and "Verifier headroom").

- **Tree**: `main` at `7f4834ce` (after #635): the S1 lots 1.1–1.4,
  1.6–1.8 and 1.10, and M4, M5.
- **eBPF object**: the CI artefact of that commit (`ebpf-object`), sha256
  `4a410ff354ab4c32…`, sent to each guest by `nn-lab.sh sync` and checked
  again by `nn-lab.sh verifier-check synced` (the report names the same
  sha256 on all six). No guest rebuilt it.
- **Lab**: our own QEMU for Windows guests with WHPX, 4 vCPUs and 8 GiB
  each, at most two at a time, on 2026-11-26. Each guest was uninstalled,
  left with no `.local` file, pin or drop-in, powered off and released.

## Exit criteria

| criterion | result |
|---|---|
| every program loads on all six kernels, except the documented optional ones | **met**: 0 failing on each kernel (the optional ones below) |
| every program ≤ 80 % of the 900,000-instruction gate on 5.15 and 6.1 | **met**: the highest is `module_read_file_observe`, 479,498 (53.3 %) on both |
| every stack chain ≤ 448 of 512 bytes, on every kernel | **met**: the deepest is 448 (`bpf_syscall_observe`, `fim_file_open_sensor`) |
| the exec fallback on 7.0 records an exec on every CPU | **met**: 10 of 10 on each of the 4 CPUs (live test and the installed agent) |
| privileged suites on 5.15 and 7.0 | **green**: 186 passed, 0 failed on each (5 of 5 runs) |
| prog-cost on 5.15 and 6.8 against lot 1.4's figures | 14 of 18 rows within 5 %; the 4 others are faster on 5.15 or within the run's own spread on 6.8 (same programs: no eBPF change since that measurement) |
| `.rpm` on AlmaLinux 9: install, upgrade, uninstall | **green**: `pkg-check` 30 of 30, then a cold boot with the agent and the watchdog active |

The other S1 exit criteria (golden files byte for byte after the move to
`jiff`, `cargo audit` with no `chrono` exception) are not lab checks: the
gates and the CI of every pull request cover them.

## 1. The verifier on six kernels

`nn-lab.sh verifier-check synced` on each guest: every program of the
object loaded with the agent's own loader setup, nothing attached.
Processed instructions: `verified_insns` of `bpf_prog_info` from 5.16 on,
the kprobe on `check_max_stack_depth` on 5.15 (the count covers the program
and its global functions). Stack: the deepest call chain read back from
the loaded program.

No program is over 80 % of the gate on 5.15 or 6.1, and no chain is over
448 on any kernel. The programs "not counted" are the documented optional
ones, each for its own reason:

- the variants built for another kernel's signature of the same function
  (`dns_answer_*_ret4/5/6` for `udp_recvmsg` / `udpv6_recvmsg` with 4, 5 or
  6 parameters, `inbound_accept_ret2/4` for `inet_csk_accept`): the one
  that matches loads, the others are refused;
- the hooks a kernel does not have: `inode_set_acl` and `inode_remove_acl`
  (5.15, 6.1), `bpf_prog_load` (before 6.9: 5.15, 6.1, 6.8; the el9 kernel
  has it), the `bpf_link` iterator (5.15);
- `nn_calib_override`, where the kernel has no `bpf_override_return`
  (`CONFIG_BPF_KPROBE_OVERRIDE` off: AlmaLinux 9, Debian 12 and 13).

The el9 kernel's verifier gives the same count as 6.12's for every program
(its BPF subsystem follows the upstream one of that time). The counts lot 1.4's
PR (#629) lists for 5.15 and 6.8 are the same here, program by program: the
object's code has not changed since.

**The attach points added in S1.**

- `fentry` on `change_mnt_propagation` (lot 1.1): in the BTF, traceable
  and in kallsyms on all six kernels; loaded by the verifier and attached
  by the installed agent everywhere. `do_mount_setattr` is not traceable
  under its name on any of them (inlined, or only an `.isra` copy), which
  is why the program sits on `change_mnt_propagation`.
- the raw `sys_enter` fallbacks of the exec and file-open sensors (lot
  1.3): loaded on all six; taken only where the self-test finds a CPU the
  syscall tracepoint misses (7.0, section 2).
- `--btf-check` checks the offsets, the LSM hooks' arguments and the
  targets of the cgroup guard and of the start-in-cgroup tracker, not
  `change_mnt_propagation`: for it the census above and the verifier's load
  are the evidence on these kernels. A kernel without it would start the
  agent with a signed degradation (a propagation change then followed at
  the guard's next refresh, not at once).

**`sensor-feasibility` on 7.0.** The lab runner's case "exec of
`/usr/bin/true`" failed on 7.0 before it ran: there `/usr/bin/true` is a
symlink to `gnutrue` (uutils coreutils), and the runner refuses to execute
anything but a regular file. The runner now executes the file the name
resolves to (`crates/nn-linux/src/sensor_feasibility.rs`, test
`a_system_binary_behind_a_symlink_runs_as_the_file_it_names`); the other
17 properties held on 7.0 as on the other five kernels.
